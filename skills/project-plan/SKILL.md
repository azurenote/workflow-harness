# project-plan - Write Plan

## Trigger Conditions

Apply this skill in the following situations:
- Codex receives `$project-plan <task description>` or a request such as "use the project-plan skill for <task description>"
- The user describes a new feature, bug fix, or task
- Keywords such as "plan", "planning", "design", "implement this", or "add this"
- At the start of any task that needs codebase analysis plus documentation

## Read Settings

Run the "Read Settings" procedure in `~/.claude/skills/SKILL-CONFIG.md` first.

## Output Language Guard

Plans generated by this skill must be written in Korean by default, even though this `SKILL.md` is written in English.
Keep canonical section headings such as `Intent Summary`, `Current State`, and `Task Cards` in English because downstream workflow skills depend on them, but write the title, prose, checklists, rationale, DoD items, task intent, validation notes, and risk notes in Korean.
Do not translate an existing Korean plan into English when registering it as an issue. Switch plan prose to another language only when the user explicitly asks for that output language.
Before finalizing a generated plan, verify that the body fields contain Korean prose. If the generated artifact drifted into English prose, rewrite it in Korean before continuing.

## Instructions

**1. Confirm task description**

1. If `$ARGUMENTS` exists, use it as the task description.
2. Otherwise, extract it from recent conversation messages.
3. If neither exists, ask the user.

**2. Analyze the codebase**

Infer scope from the task description and explore the related files/modules.
- Use an Explore agent to analyze related source files.
- Understand dependencies, interfaces, and data structures.
- Check existing patterns and coding conventions.

**3. Create plan-draft-<slug>.md**

Filename rules:
- **Draft (unregistered, canonical)**: `plan-draft-<slug>.md`
- Generate the slug from the task description automatically (3-5 lowercase English words, hyphen-separated)
- Example: "Implement JWT auth Lambda" -> `plan-draft-jwt-auth-lambda.md`
- **Slug collision**: if the same slug file already exists, add `-2`, `-3`, etc.
  - Example: `plan-draft-jwt-auth-lambda-2.md`
- For compatibility with the existing harness, `/issue` still recognizes `plan-<uuid>.md` drafts, but new plans should be created as `plan-draft-<slug>.md`.

```bash
mkdir -p .task/plan
grep -q "^\.task/plan/" .gitignore || echo ".task/plan/" >> .gitignore
SLUG="<convert-task-description-to-3-5-word-english-slug>"
PLAN_FILE=".task/plan/plan-draft-${SLUG}.md"
# Add a suffix on collision
N=2
while [ -f "$PLAN_FILE" ]; do
  PLAN_FILE=".task/plan/plan-draft-${SLUG}-${N}.md"
  N=$((N + 1))
done
```

Split the file structure into two layers.

- **Human layer**: lets the director confirm the intent, current state, target state, non-goals, and dangerous misunderstandings in the first screen.
- **Agent layer**: lets the implementation agent follow files, contracts, per-task completion conditions, and validation methods.

Leading frontmatter is **optional** and should be written only for sub-issues.
The skeleton below uses canonical English headings; fill every placeholder with Korean prose unless the user explicitly requested another language:

```markdown
---
base_branch: feat/issue-364-strategy-engine-lua   # PR review/merge target. Omit, or use project default base, for the default
parent_issue: 364                                  # optional - parent user-story issue number
---
# Plan: <title>

## Intent Summary
<Summary that lets the director confirm work intent within the first 30 lines: what changes and why.>

## Current State
<Current system/docs/workflow behavior.>

## Target State
<Desired state after the work.>

## Non-Goals
- <Things intentionally excluded from this work>

## Drift Guards
- <Points the agent is likely to misunderstand dangerously, or scope boundaries not to cross>

## Review Profile
- Profile: `auto`
- Expected mode: `<full | docs-light>`
- Reason: <docs-light for docs-only work; full when code/tests/build/CI/dependencies/runtime config are expected to change>

## Requirements
- [ ] <requirement 1>
- [ ] <requirement 2>

## Definition of Done
- [ ] <specific, verifiable condition>

## Implementation Contract
<Do not write code-level algorithms. State required interfaces, file boundaries, and compatibility contracts.>

## Task Cards

### Task 1: <name>

Intent:
<How this task contributes to the overall goal>

Files / Modules:
- <path or module>

Implementation Contract:
- <Required behavior/interface/compatibility>

Validation:
- <Test or manual verification>

Drift Guard:
- <Interpretation or scope expansion that must not happen>

### Task 2: <small task name>

Intent:
<For small tasks, Intent, Files / Modules, and Validation are enough.>

Files / Modules:
- <path or module>

Validation:
- <verification method>

## Validation Plan
- <main automated validation command>
- <needed manual review checks>

## Scope
- Files to modify: <list>
- Modules affected: <list>
- Breaking changes: Yes / No

## References
<API docs, related issues, cautions>
```

Rules:
- `Intent Summary`, `Current State`, `Target State`, and `Non-Goals` must be readable within the first 30 lines.
- A plan is not an ADR. Long-term architecture decisions belong in ADRs; the plan shares work intent and execution contracts.
- Do not put code-level algorithms in the plan. Do specify file/module boundaries, interfaces, compatibility, and validation contracts so the agent does not drift.
- `Task Cards` are not compressed checklists; they are execution contracts per task. Fill every field for large tasks. For small tasks, `Intent`, `Files / Modules`, and `Validation` are enough.
- Make the Definition of Done detailed because `$project-done` later uses it as the verification standard.
- `Review Profile` follows the shared policy in `~/.claude/skills/SKILL-CONFIG.md`. The default is `auto`; record the expected mode and reason at planning time.
- Docs-only examples: use `docs-light` when only `docs/**/*.md`, `content/**/*.mdx`, or static documentation assets are touched.
- Code-impact examples: use `full` when `src/**`, `tests/**`, build/CI/dependency/runtime config is included.
- If judgment is ambiguous, choose `full`, not the cheaper mode.

**Declare base branch (frontmatter):**
- If this work is a **sub-issue** of a larger user story and will be merged into the parent issue's **integration branch** instead of directly into the project default base, declare it in leading frontmatter:
  - `base_branch`: PR review/merge target branch, such as the integration branch name `feat/issue-364-strategy-engine-lua`.
  - `parent_issue`: parent user-story issue number, for example `364`.
- This declaration becomes the **single source of truth** for `/start` and `/done` base handling. `/issue` uploads the whole plan into the issue body, so it is automatically included in the issue description, and `/start` only **reads** this value without inference.
- For **normal work** that merges directly into the project default base, omit frontmatter (or set `base_branch: <project default base>`). Omission preserves existing behavior.
- If you do not know the integration branch name, look up candidates by parent issue number `<P>` and have a human confirm it. This is a planning-time proposal, not runtime inference:
  ```bash
  git branch -a --list "*feat/issue-<P>-*" "*feat/<P>-*"   # local/remote integration branch candidates
  ```
  For an already registered sub-issue, `.claude/scripts/harness_cli.py get-parent <sub-issue>` can confirm the parent issue (otherwise returns `{"parent": null}`).

**Korean Output Regression Check**

Before handing the plan to `$project-issue`, verify that title/prose, requirements, DoD items, task intents, validation notes, and drift guards are Korean. If these sections are English, rewrite them in Korean first.

**4. Review the plan according to Review Profile**

Read `## Review Profile` and finalize the review mode using the shared policy in `~/.claude/skills/SKILL-CONFIG.md`.

- `full`: perform adversarial plan review from architect, implementer, and test engineer viewpoints.
  - **Architect**: architecture fit, consistency with existing patterns, extensibility
  - **Implementer**: implementation feasibility, missing edge cases, conflicts with existing code
  - **Test engineer**: testability, DoD verifiability, missing test scenarios
- `docs-light`: run a single documentation review pass for reader comprehension, factual fidelity, link/path/command accuracy, and docs-as-code structure contracts.
- `auto`: resolve to `docs-light` for docs-only work; resolve to `full` when code/tests/build/CI/dependencies/runtime config changes, or when uncertain.

Collect feedback, revise and finalize the plan, and include the selected profile/mode and rationale in the output.

**5. Output**

- full path of the created file, for example `.task/plan/plan-draft-jwt-auth-lambda.md`
- flagged uncertainties
- next step: `$project-issue`
