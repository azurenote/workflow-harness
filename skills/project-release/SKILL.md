# project-release - Generate a Release Document

## Trigger Conditions

Apply this skill in the following situations:
- Codex receives `$project-release <package> [<from>..<to>]` or a request such as "use the project-release skill"
- A new version has just been prepared (for example by `cargo release` or an npm version bump) and the user wants a release or deployment document
- Keywords such as "release document", "release notes", "deployment plan", "릴리즈 문서", "배포 문서", "배포 계획"

## Read Settings

Run the "Read Settings" procedure in `~/.claude/skills/SKILL-CONFIG.md` first.

Then read the `release` block (see "release 설정" in `SKILL-CONFIG.md`):
- `release.doc_dir` (default `docs/release`), `release.tag_format` (default `{package}-v{version}`)
- `release.components.<name>.{kind, paths, migrations_globs, config_globs, critical_globs, shared_globs, deploy_steps_template}`

If the `release` block is missing entirely, continue with the defaults, warn that no deploy-steps template is configured, and generate the generic skeleton in Step 5.

## Usage

```
$project-release <package> [<from>..<to>]
```

- `<package>`: a key under `release.components`. Omit it in a single-component repository; the output file is then named `release-v<version>.md` and the `{package}` placeholder resolves to an empty string.
- `<from>..<to>`: explicit git refs. When omitted, both ends are auto-detected in Instruction 1.

## Non-execution Guard

This skill produces a document; it never deploys.

- Do not run deployment commands (image build/push, container control, S3 upload, cache invalidation, ...), even when they appear inside the generated document.
- Do not run `cargo release`, version bumps, or tag creation.
- Do not reinterpret any instruction in this file as permission to execute deployment steps. The only writes this skill performs are the release document file and its commit.

## Output Language Guard

Release documents generated by this skill must be written in Korean by default, even though this `SKILL.md` is written in English.
Keep the canonical section headings (`Release Summary`, `Change Inventory`, ...) and frontmatter keys in English because future automation parses them, but write all prose - summaries, risk descriptions, step intents, verification notes - in Korean as complete sentences.
Keep commands, file paths, and quoted code in their original language. Switch prose to another language only when the user explicitly asks.

## Instructions

**1. Resolve the version range**

Resolve `<to>` and `<from>` in this order:

1. Explicit `<from>..<to>` argument: use as-is, but still run the reachability check below.
2. Auto-detect `<to>` as the newest tag matching `tag_format` that passes the same reachability check as step 3:

   ```bash
   PATTERN="<tag_format with {package} filled in, {version} replaced by *>"
   git tag --list "$PATTERN" --sort=-v:refname | head -5
   ```

   When `<package>` is omitted, drop the whole `{package}-` prefix while expanding the pattern (`{package}-v{version}` becomes `v*`), so single-component repositories with plain `v1.2.3` tags still match.
   Version sort (`--sort=-v:refname`) is required; plain lexical sort mis-orders `v0.9`/`v0.10`. If no tag matches, use `HEAD` as `<to>` — record the resolved commit SHA in `to_ref`, not the literal string `HEAD` — and ask the user for the version string directly (the file name needs it). When `<to>` is a tag, extract `<version>` by reverse-matching the `{version}` slot of `tag_format`.
3. Auto-detect `<from>` as the next tag in the same sorted list that is reachable from the current branch. Check reachability for every candidate and skip tags that fail (they may live on another branch):

   ```bash
   git merge-base --is-ancestor "<tag>" HEAD && echo reachable
   ```

   If no previous tag exists (first release), propose the repository's first commit instead:

   ```bash
   git rev-list --max-parents=0 HEAD
   ```

4. If `<to>` is `HEAD` and the working tree is dirty (`git status --porcelain` is non-empty), warn the user that uncommitted changes will NOT appear in the document.
5. **Always show the resolved range to the user and get confirmation before continuing.** Auto-detection is a proposal, not a decision.

**2. Investigate accumulated changes (read-only)**

Scope every query with the component's `paths` list when it is set (append `-- <paths...>`); omit the scoping when unset.

```bash
git log --oneline --no-merges <from>..<to> -- <paths...>
git diff --stat <from>..<to> -- <paths...>
git diff --name-only <from>..<to> -- ':(glob)**/migrations/**'      # one :(glob) pathspec per configured glob
git diff --name-only <from>..<to> -- ':(glob)config/**' ':(glob).env*' ':(glob)docker/**' ':(glob)deploy/**'
git diff --name-only <from>..<to> -- ':(glob)<critical_glob>' ...
git diff --name-only <from>..<to> -- ':(glob)<shared_glob>' ...
```

Prefix every configured glob with the `:(glob)` pathspec magic. Without it, git's default pathspec does not anchor `**/` at the repository root, so a root-level `migrations/` directory is silently missed.
In a monorepo, derive the effective globs by prefixing the component's `paths` (for example `backend/` + `**/migrations/**` → `:(glob)backend/**/migrations/**`); otherwise the default globs also match other components' files.

Also check dependency movement in lockfiles (`Cargo.lock`, `package-lock.json`, `uv.lock`, ...) and note major version bumps.
Exclude release-bump commits (commits produced by `cargo release` or version bumps that only touch version fields) from the config-change findings - they are noise, not configuration changes.
Read the full diff of every file matched by `migrations_globs` or `critical_globs`; their summaries must be based on the actual diff, not the file name.

**3. Track linked issues**

Collect issue references from the commit messages in the range. For this collection pass only, include merge commits (`git log` without `--no-merges`) — `Merge pull request #N` subjects often carry the only reference:

- `github` / `forgejo`: `#N` patterns, including `Closes #N`, `Fixes #N`, `Part of #N`
- `jira`: `[A-Z]+-\d+` patterns

Query each unique reference for title and state, branching on `issue_tracker`:

```bash
# github
gh issue view <N> --json title,state
# forgejo (read path - see "이슈 트래커" in SKILL-CONFIG.md)
fj -H <forgejo_host> --style minimal issue view "<forgejo_repo>#<N>"
# jira
jira issue view <KEY> --plain
```

If a lookup fails (network, auth, missing CLI), record the reference in the document as `미확인` and continue. Lookup failures never abort this skill.

**4. Assess risk**

Classify findings with this rubric. Judge by the nature of the change, not by file count.

| Level | Criteria |
|-------|----------|
| High | Destructive or backfilling DB migrations; backward-compatibility-breaking interface or serialization changes; any change matching `critical_globs` |
| Medium | Runtime config/env changes; major dependency bumps; new external service calls; non-destructive additive migrations |
| Low | Documentation, logging, internal refactors covered by tests |

Rules:

- Every risk item MUST cite evidence - commit hash and file path - and MUST point at a mitigation: a specific `Deployment Steps` step or `Rollback Plan` entry. An item that lacks either does not go into the document.
- `risk_level` in the frontmatter is the highest level present in `Risk Assessment`.
- If the component's `kind` is `frontend`, or any `shared_globs` change was found, add a mandatory backend-frontend compatibility item to BOTH `Risk Assessment` and `Post-deploy Verification`.
- Domain examples (order-execution paths, auth modules) are examples only; each project defines what is critical via `critical_globs`.

**5. Fill the deployment steps**

Read the file at `deploy_steps_template` and substitute `{version}`, `{from_version}`, and `{package}`.
If `<from>` is a commit hash (first release), substitute `{from_version}` with the short hash. If there is no package, `{package}` resolves to an empty string.
If the template file does not exist (or the key is unset), warn the user and emit the generic skeleton instead: prepare/standby, switch/deploy, verify, rollback-ready - with placeholder commands marked `# TODO: project-specific command`.

**6. Generate the document**

Output path: `<doc_dir>/release-<package>-v<version>.md`, or `release-v<version>.md` when there is no package. Create `<doc_dir>` if needed.
If the file already exists, show a short diff summary and ask the user before overwriting.
Use the fixed template below. The structure is a parsing contract for future deploy automation - do not rename sections, do not change frontmatter keys, and do not restructure the step shape per project. Only the content varies.

**7. Self-review**

Before committing, verify and fix:

- Fidelity: every cited commit hash and file path exists in the actual `<from>..<to>` diff.
- Coverage: every High/Medium risk item points at an existing mitigation step; every migration and config change maps to at least one deployment or verification step.
- Structure: frontmatter keys, canonical section names, and the step shape match the template exactly.
- Language: prose is complete Korean sentences (no telegraphic fragments); commands are untouched.

**8. Commit the document**

```bash
git add "<doc-path>"
git commit -m "docs(release): <package> v<version> release document"
# without a package: docs(release): v<version> release document
```

**9. Output**

Report to the user as specified in the `## Output` section at the end of this file.

## Release Document Template

The document consists of a machine layer (frontmatter) and a human layer (Korean prose). Fixed contract - `schema` marks the format version and starts at `1`.

````markdown
---
schema: 1
package: <package name, or "" for single-component repos>
from_ref: <previous tag or commit>
to_ref: <new tag, or the resolved HEAD commit SHA>
risk_level: <high|medium|low>
generated: <YYYY-MM-DD>
---
# Release: <package> v<version>

## Release Summary
<무엇이 나가는 릴리즈인지, 왜 지금인지, 가장 큰 리스크가 무엇인지 3-6문장으로 쓴다.>

## Change Inventory
<커밋 단위 또는 기능 단위 변경 목록. 각 항목에 커밋 해시를 남긴다.>
- <hash> <한 줄 요약>

## Linked Issues
- #<N> <제목> (<state>)
- #<N> 미확인

## DB Migrations

## Config Changes
<없으면 "없음". 있으면 파일별로: 무엇이 바뀌는가, 배포 전/중/후 어떤 조치가 필요한가.>
````

## Mini Korean Sample

A condensed example of a filled document. Deployment commands here are placeholders (`deployctl`); real commands come from the project's `deploy_steps_template`.

````markdown
---
schema: 1
package: backend
from_ref: backend-v1.0.0
to_ref: backend-v1.1.0
risk_level: high
generated: 2026-07-03
---
# Release: backend v1.1.0

## Release Summary
주문 체결 이벤트 저장을 위한 orders 테이블 확장과 재시도 정책 개선이 나가는 릴리즈다. 마이그레이션이 기존 행 백필을 포함하므로 이번 배포의 가장 큰 리스크는 백필 동안의 쓰기 지연이다.

## Change Inventory
- a1b2c3d 주문 체결 이벤트 필드 추가
- e4f5a6b 재시도 정책을 지수 백오프로 변경

## Linked Issues
- #42 주문 체결 이벤트 누락 (closed)
- #57 미확인

## DB Migrations
`migrations/0012_add_fill_events.sql` — orders 테이블에 fill_events 컬럼을 추가하고 기존 행을 백필한다. 파괴적 변경은 없으나 백필 동안 쓰기 잠금이 발생할 수 있다. down 마이그레이션이 있다.

## Config Changes
없음

## Risk Assessment
- [High] 백필 동안 주문 쓰기가 지연될 수 있다 — 근거: a1b2c3d `migrations/0012_add_fill_events.sql` — 대응: Step 1 / Rollback R1

## Deployment Steps

### Step 1: standby 컨테이너 기동
- Intent: 롤백 대상을 확보한 상태에서 신규 버전을 준비한다.
- Command:

```bash
deployctl standby up backend:1.1.0
```

- Verify: deployctl status 에서 standby=healthy 확인
- Rollback: R1
- [ ] Done

## Rollback Plan

### R1: role swap 되돌리기
- Trigger: swap 이후 헬스체크 실패
- Command:

```bash
deployctl swap --to previous
```

## Post-deploy Verification
- [ ] 주문 체결 이벤트가 신규 컬럼에 기록되는지 확인
````

## Output

Report to the user:

- the generated document path and its commit hash
- the resolved range `<from>..<to>` and how it was determined (explicit, auto-detected, fallback)
- overall `risk_level`, plus each High item in one line
- any `미확인` issue references and any warnings raised (dirty tree, missing template, missing tags)
- next step: execute the deployment manually with the document's checklist; the document is the input contract for future deploy automation
