# project-adr - Write an Architecture Decision Record

## Trigger Conditions

Apply this skill in the following situations:
- Keywords such as "ADR", "architecture decision", or "design document"
- Internal call from `$project-start <id> adr` or `$project-done <id> adr`
- A significant design choice needs to be recorded

## Read Settings

Run the "Read Settings" procedure in `~/.claude/skills/SKILL-CONFIG.md` first.

Use `adr_dir` as the ADR storage path (default: `docs/adr`).

## Usage

```
$project-adr <issue-id>
```

Run independently, or as an internal call from `$project-start` / `$project-done`.

## Output Language Guard

ADR documents generated by this skill must be written in Korean by default, even though this `SKILL.md` is written in English.
Keep code identifiers, command names, API names, and quoted source text in their original language, but write the ADR title, field labels, prose, trade-off descriptions, and review notes in Korean.
Do not translate ADR output to English unless the user explicitly requests an English ADR.

## Instructions

**1. Decide ADR Content**

Read `.task/plan/plan-<issue-id>.md` and the current branch diff to identify the architecture decision that should be documented.
If the decision title is ambiguous, confirm it with the user.

**2. Decide File Name**

The ADR convention is defined in `<adr_dir>/README.md`.

- Location: `<adr_dir>/` (the `adr_dir` value from `skill-config.yaml`)
- File name: `YYYY-MM-DD-<slug>.md`
- Example: `2026-05-24-global-skills-config-layer.md`

**3. Write the ADR Document**

```markdown
# ADR: <결정 제목>

**날짜**: YYYY-MM-DD
**상태**: 제안 | 수락 | 폐기 | 대체됨
**영향 범위**: `<변경 대상 파일/모듈>`
**키워드**: keyword1, keyword2

---

## 배경 (Context)
<문제 상황. 왜 결정이 필요한가?>

## 결정 (Decision)
<내린 결정. 능동적 문장으로.>

## 대안 검토 (Alternatives Considered)
| Option | Reason Rejected |
|--------|----------------|
| <대안> | <기각 사유> |

## 결과 (Consequences)
### 긍정적
- <이점>

### 부정적 / 트레이드오프
- <트레이드오프>

## 참조
- <관련 이슈, 문서 링크>
```

**3.5. Readability and Self-containment Check (Self-review Before Commit)**

Before committing the draft, review and revise it using the criteria below. The goal is a Korean document whose prose closes the decision, rationale, and trade-offs without requiring the reader to open the code. Do not use noun piles or telegraphic phrasing (abbreviated phrasing that chains clauses with arrows or colons and omits predicates). Write every item as a complete Korean sentence with a subject and predicate that agree.

- **Define identifiers and acronyms**: When a code identifier, acronym, or domain neologism first appears, define it in the same sentence with one phrase, for example `PEL(Pending Entries List - 전달됐으나 ack 되지 않은 엔트리)`. Do not postpone definitions or offload them to external knowledge. When the document language and code language differ, define the concept in Korean and then use that term consistently.
- **Code references are not definitions**: A line reference such as `executor.rs:940` only supports prose explanation. The prose must first explain what the identifier is and why it matters.
- **Split sentences**: Break run-on sentences with more than three chained clauses, and telegraphic bullets that connect clauses with arrows, colons, or multiplication signs, into multiple complete sentences.
- **One term per concept**: Use one term consistently for the same subject. Do not repeat the same meaning in Korean and English, such as `정방향 재유도(forward 재유도)`.
- **Explain code blocks in prose**: Keep code, SQL, and pseudocode blocks in their original English text, but add prose immediately before or after the block explaining which part is relevant.
- **Fidelity and stale-text correction**: While revising for readability, verify factual fidelity. Compare against the current diff and code, correct stale statements and misquoted code lines, and ensure ADR numbers or list sequence numbers are not duplicated.

Finally, reread the document from the perspective of a reader who has never seen the code, and catch blockers such as undefined identifiers, broken causality, or subject-predicate mismatch. Always do this self-reread. If the decision is large or subtle, ask a cold-reader agent (a reader who has not seen the code) to perform the same read-through and a separate fidelity agent to compare the document against the current code. Record the result of this revision in complete Korean sentences, not telegraphic notes.

**4. Post an Issue Comment**

Markdown backticks can be interpreted by the shell as command substitution. After the ADR path is finalized, pass the entire comment body as one quoted argument.
In Codex, if a GitHub API call fails because of network or sandbox errors, immediately rerun the same command with `require_escalated`.

```bash
ADR_PATH="<adr_dir>/YYYY-MM-DD-<slug>.md"
COMMENT="ADR recorded: \`${ADR_PATH}\`"

# GitHub (harness_enabled: true)
<harness_cli> add-comment <issue-id> "$COMMENT"
# GitHub (gh fallback — no project.py layer in between)
gh issue comment <issue-id> --body "$COMMENT"
# Jira
jira issue comment add <ticket-id> "$COMMENT"
```

When running `exec_command` in Codex with the final path directly embedded, use single quotes like this:

```bash
.claude/scripts/harness_cli.py add-comment 326 'ADR recorded: `docs/arch-decision-record/2026-06-07-blue-green-swap-orchestration.md`'
```

**5. Commit the ADR File**

The ADR is included in the source tree and committed.

```bash
git add "<ADR_PATH>"
git commit -m "docs(adr): <decision title>

Related to #<issue-id>"
```

**6. Output**

- ADR file path
- issue comment URL
- if run independently, next step: continue with `$project-start` or `$project-done`
