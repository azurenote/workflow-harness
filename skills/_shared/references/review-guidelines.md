# 리뷰 가이드라인 주입 (`review_guidelines`)

리뷰 단계가 각 역할에게 **무엇을 읽히고 무엇을 보게 할지**를 프로젝트가 선언하는 자리다.
스킬은 리뷰를 지휘하되 근거를 내장하지 않는다 — 근거는 프로젝트 상수이고, 프로젝트 상수는
이 파일에만 둔다.

#### 왜 `AGENTS.md` 가 아닌가

`AGENTS.md` 는 세션 내내 켜져 있는 ambient 컨텍스트다. 필요한 것은 **리뷰 시점에만** 켜지는
단계 지시다. 근거 문서 수십 KB 를 ambient 로 올리면 `project-clean` 도 같은 값을 치른다.
더 중요한 건 세 가지다.

- **역할별 주소지정이 안 된다.** 필요한 것은 "리뷰어가 규칙을 알아야 한다"가 아니라
  설계자→어느 문서·어느 절, 구현자→어느 절, 테스트 엔지니어→어느 절이라는 **매핑**이다.
  평평한 ambient 파일은 이걸 표현할 수 없다.
- **검증이 안 된다.** 스킬은 ambient 컨텍스트가 실제로 로드됐는지, 서브에이전트가 그걸
  상속했는지 단언할 수 없다. 경로 목록은 impl-report 에 그대로 되받아 적을 수 있다.
  **위임은 받는 쪽이 실제로 할 수 있을 때만 위임이다.**
- **복제는 갈라진다.** 내용을 복제한 `AGENTS.md` 는 이미 `CLAUDE.md` 와 갈라진 전례가 있다.
  포인터만 둔 곳은 갈라지지 않았다.

따라서 `AGENTS.md` 에는 "리뷰 근거 목록은 `.claude/skill-config.yaml` 의 `review_guidelines`
에 있다" 한 줄만 둔다. 내용을 복제하지 않는다.

#### 스키마

```yaml
review_guidelines:
  common: [docs/guidelines/coding-rules.md]        # 모든 역할이 읽는다
  roles:
    architect:
      docs: [docs/guidelines/domain-types.md]
      focus: "§0 레이어 경계 · §4 중복 방지 · §11 리팩터가 드러낸 결함"
    implementer:
      focus: "§1 보안(#[instrument] 자동 인자 기록) · §3 함수 크기 · §10 검증 주장"
    tester:
      docs: [docs/guidelines/db-conventions.md]
      focus: "§10 — 가드가 변이로 검증됐는지"
```

- `common` — 모든 역할이 읽는 경로 목록. 생략 가능.
- `roles.<name>.docs` — 그 역할만 읽는 경로 목록. 생략 가능.
- `roles.<name>.focus` — 그 역할이 무엇을 볼지 적은 **자유 문자열**.

#### 해석 규칙

- **`focus` 를 파싱하지 말 것.** `§1 보안(#[instrument] …)` 같은 문자열은 특정 프로젝트의
  상수다. 스킬이 이걸 해석하기 시작하면 그 순간 언어·프로젝트 종속이 된다. 스킬은 `focus` 를
  **원문 그대로 리뷰어에게 전달만** 한다.
- **역할 이름을 고정하지 말 것.** `roles` 아래에 선언된 키를 그대로 순회한다. 프로젝트가
  네 번째 역할을 선언하면 네 명이 리뷰한다.
- `review_guidelines` 키가 없거나 `roles` 가 비면 문서화된 기본 3역할(architect ·
  implementer · tester)로 degrade 한다. 리뷰를 건너뛰지 않는다.
- **존재하지 않는 경로는 경고 후 건너뛴다.** 리뷰 자체를 중단하지 않는다. 경고는 최종 보고에
  남긴다 — 조용히 빠지면 근거 없는 리뷰가 근거 있는 리뷰로 보고된다.
- 체크리스트 사본을 만들지 말 것. 리뷰어는 경로를 **읽는다**. 요약본을 스킬이나 플랜에
  베껴 두면 정본과 갈라진다.
- 실제로 읽힌 경로 목록을 impl-report 에 기록한다. 위임이 닫혔다는 유일한 증거다.

#### 기본 역할의 기본 focus

**여기가 정본이다.** 스킬 본문에 이 표를 베껴 두지 말 것 — 아래 "해석 규칙" 이 금지하는
바로 그 사본이고, 실제로 한 번 갈라진 적이 있다.

프로젝트가 `focus` 를 선언하지 않은 역할에 아래를 쓴다. 리뷰 대상이 다르면 묻는 것도 다르다.

**구현 리뷰** (`project-start` §8) — 코드가 존재한다:

| 역할 | 기본 focus |
|------|-----------|
| architect | 아키텍처 적합성, 기존 패턴과의 일관성, 범위 준수 |
| implementer | 로직 결함, 보안, 엣지 케이스 |
| tester | 누락된 테스트, DoD 충족, **가드가 변이로 검증됐는지** |

**플랜 리뷰** (`project-plan` §4) — 코드가 아직 없다. 플랜이 **실행 가능하고 검증 가능한가**를 묻는다:

| 역할 | 기본 focus |
|------|-----------|
| architect | 아키텍처 적합성, 기존 패턴과의 일관성, 확장성 |
| implementer | 구현 실현 가능성, 누락된 엣지 케이스, 기존 코드와의 충돌 |
| tester | 테스트 가능성, DoD 검증 가능성, 누락된 테스트 시나리오, **각 DoD 항목이 실제로 실패할 수 있는지** |

#### 변이 검증 의무는 역할 선언과 무관하게 남는다

"가드가 변이로 검증됐는지" 는 tester 기본 focus 의 한 항목이 아니라 **리뷰 단계 자체의
의무**다. 프로젝트가 `roles` 를 선언해 기본값이 쓰이지 않을 때도, 역할 이름을 tester 가
아닌 것으로 바꿨을 때도, 역할이 넷일 때도 남는다. 어느 역할이 그 의무를 지는지는 프로젝트가
정하지만, **아무도 안 지는 상태는 허용되지 않는다.**

통과 사실은 가드가 작동한다는 증거가 아니다 — 가드가 막는 것을 실제로 깨뜨렸을 때 빨개지는지
확인해야 그때 충족이다. 리뷰 보고에는 초록이라는 사실이 아니라 **수행한 변이**를 적는다.
